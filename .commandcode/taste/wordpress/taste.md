# wordpress
- Omit `function_exists()` guards for WordPress 6.6+ APIs and `did_action( 'init' )` checks. Confidence: 0.80
- Guard third-party plugin API calls (e.g., `wc_get_order()` for WooCommerce) with `function_exists()` when the plugin may not be active — unlike WP core APIs, optional plugins can be absent, so the code must degrade safely. Confidence: 0.70
- Make non-trivial behaviors customizable via WordPress filter/action hooks so other code can disable or extend them. Confidence: 0.80
- Prefer minimal, binary on/off hooks over overly granular or configurable filter APIs; avoid adding hooks for every sub-decision when a simple toggle suffices. Confidence: 0.75
- Guard plugin bootstrap files against direct access with a `defined( 'ABSPATH' )` check. Confidence: 0.60
- For REST API `permission_callback`, use restrictive capabilities (e.g., `edit_post`) rather than broad read permissions when the data may be sensitive. Confidence: 0.60
- When reimplementing behavior that mirrors a WordPress/WooCommerce core API (e.g., meta value updates), match the core's semantics — including SQL type coercion, WC's already-unserialized meta values, and WP's `update_metadata()` auto-unslash contract (apply `wp_unslash()` before passing form values to WC's `add_meta_data()`/`update_meta_data()`/`delete_meta_data_value()` to avoid double-escaping quotes) — rather than using strict PHP comparisons or re-serializing logic that behaves differently from core. Confidence: 0.75
- Pass scalar IDs (e.g., `$post->ID`) rather than objects (e.g., `WP_Post`) to `current_user_can()`/capability checks, because third-party `map_meta_cap` filters (e.g., WooCommerce HPOS `HposOrderCapabilityHelper` calling `absint()` on the arg) may assume scalar arguments and fatal on objects; add a comment explaining this compatibility rationale. Confidence: 0.60
- Prefer high-level WordPress APIs over lower-level ones when their data is already primed (e.g., `get_the_post_thumbnail_url()` instead of `wp_get_attachment_image_url()` on an ID, `array_map( 'get_post_thumbnail_id', $posts )` instead of a manual `get_post_meta( ..., '_thumbnail_id' )` loop), as long as no extra query is introduced. Confidence: 0.70
- Question manual cache invalidation (e.g., `clean_post_cache()` after a thumbnail change) when WordPress core may already update the post's last-changed data; prefer relying on core and, if a manual call stays, guard it with an explicit condition instead of calling it unconditionally. Confidence: 0.60
